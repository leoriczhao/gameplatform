# 06 · 用例与闭环矩阵（v0.1 草案）

> 状态：草案，待用户确认。目的：把「页面稿 + 功能清单」升级为用例闭环——每个用例写清 actor、入口、主流程、分支/异常、状态、API、后置与可执行的闭环判据；设计、实现、验收都以本文件为准。
>
> 关联：01 定位与用户 · 02 功能与模块清单 · 03 信息架构草案 · 05 协作契约

## 0. 为什么要补这一层

现在的制品链是：01 旅程（粗）→ 02 功能（按模块）→ Pen 页面稿（happy path）→ 实现（对照旧代码）。缺的是用例内的闭环定义：

1. 没有「状态」定义：登录/游客、加载/空/错误、403/401、重复提交、断线重连、分页边界——设计稿只画了有数据的主状态。
2. 没有「闭环判据」：页面画完 ≠ 用例能走通。开发不知道什么算完成，只能对照旧页面「看起来像」，于是像无头苍蝇。
3. P3 主旅程跨端：训练闭环一半在浏览器外（OpenEnv/SDK/终端），页面稿天然覆盖不到；必须用检查点 + 证据定义闭环。
4. 工具不是问题：Pen / Penpot 都只是表达工具；没有用例清单时，换成 Penpot 一样会散。

## 2. 横切状态矩阵（每个用例至少检查一遍）

| 维度 | 必须覆盖的状态 |
|---|---|
| 角色 | 未登录 / 登录 / 作者本人 / 管理员 / 无权限 |
| 数据 | 加载中 / 空 / 正常 / 超长或截断 / 分页边界 |
| 错误 | 网络失败 / 401 过期 / 403 / 404 / 409 重复 / 429 限流 / 500 |
| 并发 | 重复点击 / 双开 / 对局中刷新 / 断线重连 |
| 展示 | 亮色默认 / 深色可选 / 1440 与 720 断点 |
| 证据 | 设计稿帧 / 实现截图 / 接口返回 / 复现路径 |

> 规则：只画 happy path 的页面稿不视为设计完成；每个用例至少要有「入口 → 关键状态 → 成功/失败反馈」的闭环帧。

## 4. P3 主循环闭环协议（U06，端到端）

一次会话内顺序执行并留证（模型 ID、metrics、match ID、回放链接、截图）：

1. API 就绪：GET /api/ready 返回 games 列表；GET /api/openenv/list_environments 可见。
2. 环境连接：按总览 Quickstart 复制 SDK 片段（RemoteVecEnv(game, n)）或直接连 /api/openenv/{game} WS；成功 reset/step 一次。
3. 训练/导出：本地跑最短训练示例，或使用仓库示例 ONNX；执行 export_onnx。
4. 上传托管：UI /models 上传 ONNX → 列表出现模型（记 model id）；契约不合法时看到可读错误。
5. 评估：点评估 → 返回 metrics；刷新页面后指标仍在（当前 N，需后端持久化 meta.eval）。
6. 模型挑战：发起挑战 → 对局完成 → 打开回放；不支持的游戏 UI 应禁用并说明。
7. 验证支线（可选）：网页玩一局、PvP 一局、观战一次、分享回放链接。

闭环判据：第 1–6 步全部成功且有证据；任一步失败即 U06 失败，记录失败点与错误码。
当前结论（2026-10-21）：第 5 步已修复（meta.eval 持久化）；第 6 步已用 microrts 夹具闭环（snake 仍不支持模型挑战，UI 已按能力禁用）→ 主旅程闭环通过。

## 6. 对设计/实现/验收的流程补充（建议）

1. 设计交付单位 = 用例：每个用例一帧（或多帧）闭环画布：入口 → 关键状态 → 成功/失败；必须覆盖 §2 中勾选的状态。
2. 实现完成定义 = 用例闭环判据通过：report-dev 按用例 ID 打勾并附证据（截图/URL/日志）。
3. QA 回归 = 按用例矩阵抽检：优先 P0 用例与状态矩阵。
4. Pen / Penpot 都只是工具：先有本文件，再决定工具；换工具不解决闭环缺失。

## 7. 已确认（2026-10-21）

1. 用例清单：用户确认「差不多了」——以本文件 24 个用例为基线，后续新增用例按变更记录追加。
2. U06 第 3 步验收：使用仓库示例 ONNX（docs/pm/qa/fixtures/snake-rotwin-min.onnx）走上传链路，不现场跑训练。
3. 闭环执行与验收：由 Lead 执行并留证（证据见 §8）。
4. 设计工具：暂不切换；先用用例与闭环把开发收住，工具（Pen/Penpot）另行决策。
