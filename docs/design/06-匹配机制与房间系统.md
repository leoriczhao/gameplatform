# 06 · 匹配机制与房间系统（PvP v2 重设计）

> 状态：已交付（历史设计）· 触发原因：用户反馈「PvP 不应该有房间或匹配机制吗」
> 结论：**邀请码只能算"私房"，不是一个可运行平台该有的全部。** 本文对标
> 权威对战平台（Lichess / BattleSnake / Halite / 国内棋牌房间制），给出
> 房间 + 匹配队列 + 计分体系 + 观战回放的完整设计，替代现在"只有邀请码"的 PvP。

## 1. 现状与问题

现有 PvP（`docs/design/03` 5.1 节）只有一条路：A 建房拿 6 位邀请码 → 手动发给 B →
B 输码加入。问题：

1. **没有公开房间**：大厅看不到"有人在等对手"，无法随手加入。
2. **没有快速匹配**：想打一局必须先找到人、再传邀请码，成本高、转化差。
3. **没有计分区分**：所有对局都结算 ELO，好友练手局也掉分（应支持 casual）。
4. **没有断线重连入口**：刷新页面后没有"我的进行中对局"列表可恢复。
5. **没有观战**：想围观别人的对局做不到（API 其实已支持只读 GET，缺 UI 与设计承诺）。
6. **模型没有排位**：模型对战是"手动点单"，没有自动匹配池与模型积分。

## 2. 对标平台调研（用户用例来源）

### 2.1 Lichess（国际象棋，人 vs 人匹配的标杆）

- **Quick Game（快速匹配）**：选好时限与积分池，点一下进入匹配池，系统按
  **积分范围**撮合两个 seeker，可随时取消。
- **自定义 seek（约战）**：在大厅发一个带条件（积分区间/时限/变体）的"寻战"，
  别人从列表接受；seek 有有效期。
- **casual / rated 区分**：练习局不积分，积分局才动 ELO。
- **匹配范围随时间放宽**：找不到人就逐步扩大积分区间，直到配到为止。
- 配套：认输/和棋提议/再来一局（rematch）、观战、对局回放。
- 来源：[Lichess Lobby & Matchmaking 架构](https://deepwiki.com/lichess-org/lila/3.1-lobby-and-matchmaking)、[积分范围 seek 讨论](https://lichess.org/forum/lichess-feedback/seeking-with-rating-ranges-doesnt-work)

### 2.2 BattleSnake（AI 蛇对战平台，与我们的定位最接近）

- 三层玩法：
  - **Ladder（天梯）**：常驻排位，平台持续给蛇匹配对手，胜负更新积分。
  - **Arena（竞技场）**：限时赛事，固定地图，限期内疯狂对局冲榜。
  - **Battlegrounds（约战）**：自定义对局——挑战指定对手、和好友开房、
    打内置蛇练手；支持**观战与回放**。
- 工程机制：游戏引擎每回合 HTTP 轮询你的 bot（/start /move /end）；超时（500ms）
  跳过该步，连续超时判负——"超时推进+判负"与我们现有 PvP 超时策略同构。
- 来源：[Competitive Play 指南](https://docs.battlesnake.com/guides/competitive-play)、[Battlegrounds 介绍](https://docs.battlesnake.com/blog/2022/05/17/welcome-to-battlegrounds)、[API 文档](https://docs.battlesnake.com/api/introduction)

### 2.3 Halite（AI 编程竞赛平台，模型排位的标杆）

- 用户提交 bot → 进入**匹配管理器**（match manager）→ 分配对局 → 结果回写。
- 积分用 **TrueSkill 式（mu/sigma）**而非纯 ELO：更抗运气波动，多人 FFA 也适用；
- 排行榜按技能分排序，bot 之间自动撮合。
- 来源：[Halite 积分系统报告](https://github.com/Janzert/halite_ranking/blob/master/rating-report.md)、[halite3-match-manager](https://gitlab.com/smiley1983/halite3-match-manager/-/blob/master/README.md)

### 2.4 国内棋牌房间制（房间 + 匹配的成熟范式）

- **双轨**：房间系统（房卡/创建/加入/座位/开局）与匹配系统（队列、ELO 动态分房、
  超时取消、断线重连、机器人补位）并存，职责分离。
- 断线重连协议：session id + token 恢复对局；观战席位与对局分离。
- 来源：[Go 棋牌房间匹配系统（ELO 动态分房+断线重连）](https://datasea.cn/go0211480852.html)、[房卡模式讨论](https://forum.cocos.org/t/topic/176889)

## 3. 设计目标

1. **双轨并行**：房间（U2/U3）+ 匹配（U1）是两套入口，最终都收敛到同一个"对局会话"。
2. **计分可区分**：ranked / casual；邀请码私房默认 casual，可开 ranked（U4）。
3. **复用现有引擎与会话内核**：房间/匹配只负责"撮合与参数"，进入对局后
   仍是现有 `PlaySession`（双方提交→推进 tick、超时判负、回放落库）——改动面最小。
4. **全 API 可玩**：所有新功能都有 REST 端点 + SDK，代码玩家与网页玩家平等。
5. **单容器可运行**：内存态队列与房间列表（重启丢失可接受，v2 文档明示）；
   不做 Redis/多副本（见 §9 风险）。

## 4. 核心概念：房间（Room）

Room = 现在 PvP 会话 `status=waiting` 阶段的**正式化** + 对局参数。

### 4.1 房间字段（在 PlaySession 上扩展）

```
id           会话 id（同现在）
game         microrts（v2 扩展 snake/tetris PvP 后通用）
kind         pvp
mode         ranked | casual          # 新增：是否计分
visibility   public | private         # 新增：public 进大厅列表
invite       6 位邀请码（private 的钥匙；public 也有，便于分享）
settings     {seed?, turn_ms?}        # 新增：开局参数（v1 仅 seed）
players      [p0, p1]（p1 空位可被任何人/任何好友加入）
status       waiting → active → finished | cancelled
created_at / updated_at
```

### 4.2 房间状态机

```
                 创建(visibility=public|private, mode=ranked|casual)
                              │
                              ▼
   ┌──────────── waiting（p1 空位）────────────┐
   │  public: 出现在大厅列表，任何登录用户可加入 │
   │  private: 仅凭邀请码加入                   │
   │  房主可改参数 / 取消（→ cancelled）         │
   └────────────────┬─────────────────────────┘
                    │ p1 加入（房主可选"开局"，v1 自动开局）
                    ▼
   active（进入现有 both-submit-then-tick 对局）── 结束 → finished
                              │
              resign / 超时判负 / 一方摧毁 → finished + （ranked: 结算 ELO）
```

- 与现在差别：① 公开房间可被大厅列表发现并直接加入；② 计分与否在创建时决定。
- **兼容性**：现有 `{kind:"pvp"}`（无参数）= `mode=ranked, visibility=private`
  （暂定，保持行为不变），新参数向后兼容老客户端。

## 5. 匹配队列（Quick Play，U1）

### 5.1 流程

```
POST /api/v1/{game}/matchmaking/queue {mode:"ranked"|"casual"}
  → 进入该游戏的匹配池（每人同游戏最多排 1 个队列；重复入队=更新参数）
  → 服务端每 2s 扫描：对池内任意两人，若 |ELO差| ≤ band → 撮合
  → 自动创建 room（visibility=public 的隐藏房间？否：直接用内部 room，
     mode 同请求，p0=先入队者）→ 双方 poll 到 room id → 各自进入对局
DELETE /api/v1/{game}/matchmaking/queue    取消排队
GET    /api/v1/{game}/matchmaking/status   我当前排队状态（含预计等待）
```

### 5.2 撮合算法（band 放宽，Lichess 式）

```
初始 band = 100（ELO 分差）
队列每等 5s：band = min(band + 100, 400)
等待 > 60s：band = ∞（任意对手，casual 模式下 30s 即可放宽到 ∞）
同队不匹配：双方不能来自同一个账号（多开自刷防弊）
同一对已匹配未完成时不重复撮合
```

- ranked 与 casual **分开撮合**；casual 池可跨分差任意。
- 取消排队即时生效；超时（10 分钟）自动移出队列。
- 模型排位池复用同一套 band 逻辑（见 §7）。

### 5.3 为什么不做"匹配评分模型"（MMR 预测胜率那套）

腾讯/Valve 式的预测胜率匹配依赖海量玩家同时在线与多目标优化；我们规模小，
Lichess 的**积分差 band + 时间放宽**足够公平、实现简单、可解释。v2 若人多再上
TrueSkill（Halite 式 mu/sigma），接口不变。

## 6. 计分体系（ranked / casual / 模型分）

| 对局类型 | 计分 | 备注 |
|---|---|---|
| 匹配队列 ranked | 人 ELO（K=32，起始 1200） | 现有 ratings 表 |
| 匹配队列 casual | 不计分 | 仅落 matches 记录 |
| 房间（private 好友约战） | 默认 casual；房主可开 ranked | 防好友刷分，ranked 需双方同意 |
| 房间（public 大厅加入） | 默认 casual；创建者可开 ranked | 同上 |
| 模型排位池 | **模型分**（新增 model_ratings 表） | 模型作者可见 |
| 模型约战（现有 create_match） | 不计分 | 保持现状 |

模型分设计（U8）：`model_ratings(game, model_id, rating, games, wins)`，起始 1200、
K=32；排位池内 模型 vs 模型 / 模型 vs 内置 AI（内置 AI 不占分但算战绩）。
挂池时模型 `status=queued`，作者可随时撤池（`DELETE /matches/queue/{model_id}`）。

## 7. 断线重连、观战、回放、再来一局

- **断线重连（U5）**：新增 `GET /api/v1/play/active` 返回我所有
  `waiting/active` 会话（含对手、tick、我的阵营）；前端刷新后若存在进行中对局，
  顶部横幅提示"回到对局"。断线方在 PvP 中由**现有超时策略**兜底（60s 自动空过、
  连续 5 次判负），无需新协议。
- **观战（U6）**：`GET /sessions/{id}` 已允许非玩家只读（`side:null`），正式化：
  - public 房间的对局 + 进行中的匹配对局默认可围观（全信息游戏，无信息泄露问题）；
  - 前端观战页：只读棋盘 + tick + 双方提交指示，2s 轮询（复用 PvP 页组件，隐藏操作面板）；
  - 结束后跳转回放。
- **回放（已有，补 UI）**：finished 对局的 moves 已随 `matches` 落库
  （`record_pvp_finish`），新增 `/api/v1/matches/{id}/replay` 只读端点 +
  前端回放器（BoardCanvas 逐 tick 步进/播放）。BattleSnake 的 board 播放器是参照
  （[Battlesnake Board](https://github.com/BattlesnakeOfficial/board)）。
- **再来一局（U7）**：`POST /api/v1/{game}/play/sessions/{id}/rematch`
  → 复制 settings，**互换 p0/p1**，创建新 waiting 房间，把双方带回；仅 finished
  对局可用，仅原双方可用。

## 9. 实现约束与风险

- **内存态队列/房间列表**：与现有会话一致（单容器）。重启丢失排队与等待中房间，
  active 对局也丢——v1 可接受并**在 UI 明示**；多副本/Redis 属 v2（D12）。
- **SSE 未落地**：现在靠 2s 轮询（microrts PvP 页已验证）。匹配通知同样走轮询
  （status 端点），不引入 WebSocket——改动面小；将来人多了再上 SSE/WS。
- **防刷分**：ranked 房间需双方同意 + 同账号不可匹配；ELO 只结算 1v1 真人局。
- **模型排位池的 CPU**：模型对局跑在 worker 池（现 8 并发），排位池需加
  排队上限（如每用户同游戏 1 个在排 + 全局限 20），避免挤占人 vs 人对局。

## 10. 阶段计划（M1→M5）

| 里程碑 | 内容 | 验收 |
|---|---|---|
| M1 房间系统 | 公开房间列表 + mode/visibility + join 端点 + 大厅房间页；老邀请码流兼容 | U2/U3/U4 网页可走通；causal 不计分 |
| M2 快速匹配 | 队列 + band 撮合 + 取消/状态端点 + 前端"快速匹配"按钮与排队动画 | U1：两账号排队秒配，ranked 结算 ELO |
| M3 断线重连 + rematch | active 列表、横幅恢复、rematch | U5/U7 |
| M4 观战 + 回放 | 观战页、matches replay 端点、回放器 | U6 可围观；旧局可回放 |
| M5 模型排位池 | model_ratings、模型挂池、模型分榜 | U8 挂池自动打并上榜 |
| v2（P5） | 赛季/竞技场、TrueSkill、多副本 Redis、snake/tetris PvP | U10 等 |

## 11. 决策更新（追加到 00 决策日志）

- **D6 修订**：PvP 从"邀请码会话"升级为"**房间 + 匹配队列**双轨"（本文档）。
- **D9**：匹配撮合用 **ELO 分差 band + 时间放宽**（初始 ±100，5s/档 +100，
  上限 ±400，60s 后任意），不做预测胜率 MMR。
- **D10**：对局分 **ranked / casual**；好友房默认 casual，防刷分。
- **D11**：模型积分用独立 `model_ratings` 表，与人分榜隔离。
- **D12**：队列与房间列表 v1 为**内存态**（单容器），多副本/Redis 属 v2。
