# 04 · 模型托管与对抗

## 1. 目标

用户通过环境 API 采样、在自己的机器上运行训练算法，训练好模型后**上传到平台**，
让模型代替自己参加 PvE 挑战和 PvP 对战；也可以继续用"外部 bot URL"模式
（模型留在自己机器上）。

## 2. 模型来源（三种，并存）

| 类型 | 说明 | 适用 |
|---|---|---|
| **A. 托管模型（v1 核心）** | 上传 **ONNX** 文件，平台用 onnxruntime 推理 | 想彻底托管、自动参战 |
| B. 权重+预设架构（v2） | 上传 .pt/.npz + 指定平台预设网络结构 | 不想自己导 ONNX |
| C. 外部 bot（保留现状） | 模型在你机器上，平台每步 HTTP 调用你的 URL | 快速实验、模型太大/保密 |

v1 只做 A + C。**不做代码上传/沙箱执行**（安全风险与投入不成比例，见 Q1）。

## 3. 托管模型的 I/O 契约（每游戏定义）

模型推理发生在服务端，因此每个游戏必须定义**标准观测张量 → 标准动作张量**的契约，训练 SDK 保证产出的模型符合契约。

### snake（简单：单动作 Q 值）
```
输入  obs: float32[1, 1334]      # rotwin R=10 观测（与内置 AI 完全一致）
输出  q:   float32[1, 3]         # 3 个相对动作的 Q 值 → argmax
```

### tetris（单动作 Q 值）
```
输入  obs: float32[1, 2, 20, 10] # 双通道棋盘（env grid obs）
输出  q:   float32[1, 4]         # 4 个动作 Q 值 → argmax
```

### microrts（复合动作 → 特殊处理）
每 tick 需输出**全部单位的指令**，变长输出不适合 ONNX。v1 方案：

- **方案 1（推荐，简单）**：模型每 tick 只负责**一个单位的决策**：
  ```
  输入  obs: float32[1, 6, 16, 16] + 选中单位特征(one-hot 类型/位置)  → 固定输入
  输出  logits: float32[1, 7*4*5]  # 展平 (命令×方向×生产类型) 的组合 logits
  ```
  平台轮询所有己方单位：对每个单位跑一次推理，合成整 tick 指令。单位多时较慢（10 单位 × 推理 ≈ 可接受，onnxruntime 单次 <5ms）。
- **方案 2（v2）**：图网络/变长输出，ONNX 支持有限，暂缓。

> 实际上 microrts 的 v1 建议直接用 **C 外部 bot**（SDK 提供 microrts bot 模板）；托管模型先支持 snake/tetris。

## 4. 模型记录与接口

```
models
  id          INTEGER PK
  owner_id    INTEGER（users.id）
  game        TEXT
  name        TEXT（用户命名）
  model_type  TEXT（"onnx" | "external_bot"）
  file_path   TEXT（ONNX 存储路径）/ url（外部 bot）
  io_contract TEXT（"snake.q3" | "tetris.q4" | …，决定推理封装）
  meta        JSON（训练参数/评估指标，可选）
  status      TEXT（active | deleted）
  created_at  REAL
```

接口（见 01 全景表）：
- `POST /models`：multipart 上传 ONNX + 表单（game/name/model_type）；服务端校验：文件大小 ≤20MB、ONNX 魔数、`onnxruntime.InferenceSession` 能加载、输入输出 shape 匹配该游戏的 io_contract → 否则 400
- `POST /models/{id}/eval`：模型 vs 内置 AI（3 局）→ 返回胜率/得分，写回 meta
- 配额：每用户每游戏 5 个活跃模型

## 5. 模型参战流程

### 5.1 PvE：我的模型 vs 内置 AI

`POST /{game}/play/sessions {kind:"pve", opponent:"model:123"}` → 会话内对手 = 模型 worker。
成绩 `mode="model"`，进 PvE 排行榜（与人工同榜，标记 🤖）。

### 5.2 PvP：模型 vs 模型（异步对战）

```
创建方                         服务端                        对手
 │ POST /matches {game, model_a:"我的模型id", model_b:"对方模型id"|内置AI}
 │────────────────▶ 校验双方模型/配额 → 创建 match(status=queued)
 │ 可立刻离开网页 —— worker 异步执行
 │                 后台 worker：new_state → 循环：双方各自推理 → step_state
 │                 结束 → match.status=finished + result + replay 落库
 │ ◀──────── GET /matches/{id} 查看结果与回放（任何时间）
```

- worker 并发上限：每用户 4 场；全局池上限（如 16 场并行）
- 失败处理：模型推理异常 → 该方判负 + 原因记录
- **挑战**：`model_b` 可以是"内置 AI（难度）"或"任意公开模型"或"自己的另一个模型"

### 5.3 PvP：人 vs 模型（实时）

即 PvE 会话（opponent=model:123）——平台视角统一为"单玩家+服务端对手"。

## 6. 推理 worker 实现要点

- 依赖：`onnxruntime`（CPU）；每游戏一个推理封装（`inference/{game}.py`：obs(state)→tensor、tensor→action）
- 推理线程池：onnxruntime session 是线程安全的（同 session 多线程推理），预加载活跃模型
- 模型缓存：LRU，避免每次对战重新加载
- 超时：单次推理 >1s 判异常

## 8. 开放问题

- Q1：是否接受代码上传？**v1 不做**（沙箱安全成本高），只做 ONNX + 外部 bot。
- Q5：模型的"公开"属性——是否允许其他用户挑战你的模型？v1 允许（挑战即跑一局异步对战），v2 可加隐私开关。
- Q6：模型作弊防护——托管模型是权重推理，无法作弊；外部 bot 允许自定义逻辑（算规则 bot 不算作弊，v1 明确规则：外部 bot 可读全量 state）。
