# 19 · 游戏内核抽取设计（设计 17 的 M0）

> 状态：已实现（2026-10-27，分支 `feat/local-training`，见 §11），待合并。
> 关联：设计 12/13（游戏与平台解耦，已完成）、17（对局舞台，本文是它的 M0）、18（本地训练，本文要消除它带来的代码副本）、D3（同一引擎）、D18（沙箱）、D25（包依赖白名单）。
> 发布方式：破坏性更新（沿用 D36）。对外 HTTP / WS 行为不变，改动的是代码结构和 SDK 的内部布局。

## 0. 结论

把"让游戏包按规则运行"的代码，抽成一个纯 Python 库 `gamekernel`。它只依赖标准库和 numpy，不依赖 FastAPI、SQLite 和账号体系。服务器、SDK、GDK 都导入这同一份库。外围业务只能依赖内核，内核不能反过来依赖业务，这条规则由测试强制执行。

**不拆分服务**：单容器（D12）没有扩容需求，而且网络边界会恰好落在每一步推进这条最热的路径上。

## 1. 问题

设计 12/13 解决的是"具体游戏"和平台的耦合。还没解决的是**游戏运行规则**和外围业务的耦合。

### 1.1 同一套规则存在多份副本

| 规则 | 现在的位置 |
|---|---|
| 加载游戏包 | `backend/ugc_worker.py` main、`gdk-ug/test_runner.py` load_game、`sdk/gameplatform/local.py` LocalGame._import |
| 调用游戏代码的方式（rewards 的 TypeError 回退、ai_action 回退、owner 参数回退、JSON 边界） | `ugc_worker._dispatch`、`LocalGame` |
| 一局的推进规则（reward 校验、validate→step、奖励的类型转换、done） | `openenv_native.PlatformEnvironment`、`environment_contract.checked_rewards`、`LocalVecEnv`、`local.checked_rewards` |
| 模型协议（simple / composite） | `inference.model_action`、`local.model_action` |
| 模型评估流程 | `models.evaluate`、`local.evaluate` |
| 模型契约规范化 | `inference._contract_for`、`local.contract_of` |
| game.yaml 校验 | `ugc_pack.validate_meta`（服务端）。GDK 测试器只做了宽松版，并注明"以平台上传为准" |
| 静态扫描 | `ugc_static`（只有服务端有），作者上传前在本地没法自查 |

这些副本之所以存在，是因为这些规则要在**五种环境**里运行：沙箱 worker、服务端 OpenEnv、服务端对局与评估、用户的训练机、作者本地的测试器。而它们现在写在只能在服务器上跑的模块里。

一致性测试（设计 18）能**发现**副本之间的偏差，但不能**防止**偏差产生。

### 1.2 依赖方向是反的，职责也混在一起

1. `registry.resolve` 在解析历史版本时导入了 `ugc`，也就是运行时直接读业务层的 SQLite 表。
2. `ugc.py` 同时包含包处理流水线（校验、扫描、解包、资源检查、冒烟测试、打包分发）和审核业务（配额、审核流、通知、作者身份），还导入了 `auth` 和 `social`。
3. `sessions.py` 和 `matches.py` 在游戏流程里直接调用 `growth.award_pve/award_pvp`，结算逻辑硬编码在对局代码里。
4. `inference.model_action` 依赖全局的 `registry.GAMES`，无法接收任意的游戏实例，所以 SDK 复用不了它。

## 2. 切分标准

**一段代码属于内核，当且仅当它必须在两种以上的运行环境里表现一致。** 只在服务器上运行的，就属于运行时或业务。

按这个标准判断：

- 沙箱属于服务端的部署策略，不是游戏规则，留在运行时层。
- 静态扫描是纯函数，而且作者需要在本地运行，放进内核。
- YAML 文件解析放在边缘（zip 和文件读取），内核只接收已经解析好的 dict。

## 3. 分层与依赖规则

```
L3 业务        auth · social · growth · scores · admin · ugc（审核流/配额/通知/归属）
               ↑ 订阅 events（match_finished …）       ↓ 实现 PackageStore 接口
L2 对局领域    sessions / Match actor（设计 17）· matchmaking · ratings · 服务端评估
               ↓
L1 服务端运行时 ugc_runner / ugc_worker / ugc_sandbox / ugc_proxy · registry · package_pipeline
               · openenv_native · inference（onnxruntime 外壳）
               ↓
L0 gamekernel  loader · calls · episode · models · manifest · scan       （stdlib + numpy）
               ↑ SDK（LocalVecEnv / evaluate / export）· GDK test_runner 也直接依赖这一层
```

**规则只有一条：只能向下依赖。** 新增 `tests/test_layering.py`，用 AST 扫描各层模块的 import，发现以下任一情况就失败：

- L0 导入了 L0 以外的任何平台模块，或者 FastAPI、SQLite、requests；
- L1 导入了 L2 或 L3；
- L2 导入了 L3 的业务模块（只允许通过 events 交互）。

## 4. L0 `gamekernel` 的内容

| 模块 | 内容 | 来源 |
|---|---|---|
| `loader.py` | `load_package(dir) -> adapter`：`spec_from_file_location` + `submodule_search_locations`，把包目录放进 `sys.path`，校验 `get_adapter()` | worker、test_runner、LocalGame 三份合一 |
| `calls.py` | `GameCalls(adapter)`：`new_state / step_state / validate_* / obs / obs_array / opponent_action / ai_action / sample_action / model_inputs / model_decode / info`，包含全部回退规则；`wire()` 是 JSON 边界 | `_dispatch` 的语义部分 + LocalGame |
| `episode.py` | `checked_rewards`、`environment_schemas`、`describe(info, meta)`；`Episode(calls).reset(seed, options, rewards)` / `.step(action) -> (state, reward, done)`，含 validate、奖励类型转换、done 判定 | openenv_native、environment_contract、LocalVecEnv |
| `models.py` | `contract_of(meta)`；`model_action(calls, contract, run, state, owner)`，其中 `run(x) -> y` 由调用方提供（服务端是 onnxruntime 会话，SDK 也是）；`play_eval(calls, meta, act, seeds)` 是评估流程 | inference、models.evaluate、local.evaluate |
| `manifest.py` | `validate_meta(dict)` 与 `validate_contract(meta, info)` | ugc_pack.validate_meta、contract_check |
| `scan.py` | `scan_dir` / `scan_renderer`（AST 静态扫描） | ugc_static |

约束：

- **只依赖 stdlib 和 numpy（D25）。** 模块级导入全部完成，**不能有延迟导入**，因为 worker 要在锁定文件系统之前导入内核，锁定之后就读不到内核目录了。
- **worker 的职责收缩为三件事**：导入内核 → 安装沙箱 → 在 stdin/stdout 上做 JSON IPC，并把每个 op 转发给 `GameCalls`。`new_batch / step_batch` 的批量循环也放进 `calls`。
- **内核的版本号**写在 `gamekernel.__version__`，SDK 与服务端用的是同一份源码。设计 18 的一致性测试保留下来，作为集成层面的最后一道防线。

## 5. L1 / L2 / L3 的改动

1. **registry 改为依赖接口。** 新增 `PackageStore` 协议（`resolve(slug, version) -> adapter`），由 `ugc` 在启动时注入实现。`registry.py` 不再 `import ugc`。
2. **拆分 `ugc.py`：**
   - `package_pipeline.py`（L1）：`validate_package`（zip 层校验 + 解析 YAML → `manifest.validate_meta`）、`extract`、资源检查、`scan`、冒烟测试、`package_archive`；
   - `ugc.py`（L3）：数据库表、配额、审核状态机、通知、作者身份与官方判定、`package_release` 的分发策略。
3. **`inference.py` 只保留 onnxruntime 外壳**：`load_model`、`check_contract`、`run`。协议部分改调 `gamekernel.models`，并显式传入游戏实例。
4. **新增 `events.py`（L2）**：一个进程内的同步事件总线，比如 `emit("match_finished", record)`。订阅方包括 growth（XP）、ratings（ELO）、scores（榜单）、models（评估元数据）。订阅方抛出异常时只记日志，不影响对局流程，这和现在 `except: pass` 的意图一致，但会留下记录。`sessions.py` 和 `matches.py` 不再导入 `growth`。之后设计 17 的 Match actor 也只负责发事件。
5. **openenv_native** 的 reset/step 改用 `gamekernel.episode.Episode`，只保留 OpenEnv 协议适配和限流。

## 6. 放在哪里

`sdk/gamekernel/`，作为 SDK 发行包里的第二个顶层包，与 `gameplatform` 并列。

- **用户**：仍然只需要一次 `pip install -e sdk`。
- **服务端**：Dockerfile 增加 `COPY sdk/gamekernel/ /app/gamekernel/`，并把 `/app` 加进 `PYTHONPATH`。CI 中已经 `pip install -e sdk`。
- **GDK**：`test_runner.py` 改为导入 `gamekernel` 的 `loader`、`manifest` 和 `scan`。作者在本地跑的就是平台上传时那一套校验，"以平台为准"这句说明可以删掉。

不单独发一个包的理由：没有第二个发行渠道（目前从仓库安装，不发布到 PyPI），多一个包只会给用户多加一步安装。

## 7. 迁移步骤

每一步都保持全量测试通过，而且每一步都可以单独提交。

1. 新建 `sdk/gamekernel/`，把 `calls`、`loader`、`episode`、`models`、`manifest`、`scan` **原样搬入**（先搬代码，不改逻辑），补上内核的单元测试。
2. 服务端切换到内核：worker、openenv_native、inference、ugc_pack、contract_check、ugc_static 改为调用内核，删除原有实现。
3. SDK 与 GDK 切换到内核：`local.py` 只保留下载、缓存和向量环境；`test_runner.py` 改为调用内核；删除上表列出的副本。
4. 依赖倒置：引入 `PackageStore`，拆分 `ugc.py`。
5. 引入事件总线：`sessions.py` 和 `matches.py` 的结算改为发事件。
6. 加上 `tests/test_layering.py`，更新 Dockerfile 和 CI，在本地构建镜像并启动冒烟测试。

## 8. 验收

- `test_layering.py` 通过；用 grep 确认 §1.1 表格里的每条规则只剩一份实现。
- 全量测试通过（当前 345 个），覆盖率门槛 ≥ 80% 保持；设计 18 的一致性测试全部通过。
- Docker 镜像能构建，容器能启动，`/api/ready` 正常。
- 对外 HTTP / WS 接口没有任何变化（`test_api_contracts` 不改用例）。

## 9. 与设计 17 的关系

M0（本文）排在 M1 之前。M1 的 Match actor 直接建立在 `gamekernel.episode` 和 `events` 之上：actor 只负责推进和发事件，ELO、XP、榜单各自订阅。这样 M1 不用先写一遍耦合版本再拆开。

## 10. 不做 / 风险

- **不做**：拆分成多个服务；对业务层内部做抽象；把前端的 game.yaml 渲染校验（`web/src/render/schema.js`）与 `manifest.py` 合并。后者涉及两种语言，可以以后用 JSON Schema 统一，优先级低于运行规则。
- **风险：worker 的导入时机。** 内核必须在 `sandbox.install` 之前完整导入。由 `test_ugc_isolation` 覆盖，并新增一个用例："锁定之后内核功能仍然可用"。
- **风险：搬代码时行为漂移。** 第 1 步只搬不改，并在同一个提交里跑全量测试和一致性测试。
- **对外影响**：SDK 安装后会多出一个顶层包 `gamekernel`。`LocalGame` 等公开 API 保持不变，内部改为调用内核。
