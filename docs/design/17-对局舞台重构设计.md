# 17 · 对局舞台重构设计（草案，待评审）

> 状态：草案（2026-10-23），取代 `design/game-stage-spec.md` v0.1。
> 范围：前端舞台组件 + 后端游玩会话层 + 游戏包契约增量。训练面 env API（D2）与 OpenEnv 附加面不在本次改动范围内。
> 前提：沿用 D3（同一引擎）、D12（单容器内存态）、D18（沙箱）、D26（平台零游戏名硬编码，允许破坏性重构）。
> **发布方式：破坏性更新（2026-10-26 用户拍板）**。不保留 v1 play 兼容层；后端、前端、SDK、测试在同一个版本里一起切换，旧客户端直接 404。
> **范围调整（2026-10-27 用户拍板）**：realtime 人类对战往后放，本期只实现 turn 时钟，详见 §0.1。

## 0. 结论先行

1. **舞台只有一个对象：Match（对局）**。它由一条权威帧时间线、0..n 个座位和一个时钟组成。solo、duel、spectate、replay、模型对战本质上是同一个 Match，只是"我是否有座位、时间线是否还在增长"不同。四种模式、四个页面合并为一个路由 `/m/:id` 和一个 `<Stage>` 组件。
2. **会话与对局记录合并为同一个 id**，从创建起就落库。现在的 session（内存 hex id）和 match（SQLite int id）两个 id 体系、两套回放、两个观战页一并取消。
3. **推进由服务端驱动，不再由轮询驱动**：每个进行中的对局对应一个 Match actor，由它负责计时、超时、服务端座位出招和结算。GET 请求不再有副作用。
4. **传输方式：命令走 REST，事件走 SSE**。客户端只是一个事件 reducer。断线重连、观战、回放共用同一条代码路径。这一条修订 D14，只限于对局流。
5. **时钟写进游戏契约**：`turn`（等所有该出手的座位）或 `realtime`（固定节拍推进，输入以"意图"语义保持）。倒计时和超时由此成为 API 字段，不再是隐形规则。
6. **按视角下发，不再广播原始 state**：`_` 前缀的键属于服务端私有，seed 不再下发。这样可以堵住 PvE 榜单"按 seed 预演"的漏洞，也为隐藏信息类游戏留出口子。
7. **回放是数据，不是计算**：服务端在对局结束时存帧，客户端不再通过 OpenEnv WS 重算，2000 帧的上限随之消失。

## 0.1 范围调整（2026-10-27）

产品定位（`docs/pm/01`）中的主用户是模型作者（P3），人类对战只是验证支线。本期只做直接服务 P3、或修复现有缺陷的部分。

| 本期做 | 往后放 |
|---|---|
| 统一 Match / 座位模型（AI、模型、bot 座位；模型对战并入） | **realtime 时钟**（节拍推进、意图语义、节拍合批） |
| Match actor（服务端推进、截止时间、结算集中在一处） | 断线宽限后判负的策略（presence 照常下发，只用于展示） |
| **turn 时钟**（`move_timeout_s` / `on_timeout` / `max_timeouts` 写入 game.yaml） | 聊天并入事件流（聊天接口沿用现有的 REST 加轮询，只是路径迁到 v2） |
| SSE 事件流（单一 reducer；模型对战可以实时观看） | ranked 观战延迟 |
| 服务端存帧 + `/frames`（修复长对局无法回放的问题） | 移动端底部指令面板等人类对战的打磨 |
| 视角裁剪（`_` 私有键）、统一鉴权矩阵 | |
| 再来一局改为双方确认（这是缺陷修复，不是新功能） | |
| `<Stage>` + `/m/:id`，CompositeBuilder 先做 turn 版 | |

由此带来的连带结论：

- **microrts 本期保持 turn**。人类打满 4000 tick 的问题（R1）留到 realtime 阶段解决。本期 microrts 的主要使用场景是模型对模型、人对内置 AI 的短局演示。
- **Q1 / Q2 关闭**：snake / tetris 保持"按一下走一步"，榜单不受影响，practice 与 ranked 使用同一个时钟。
- **Q3 默认不延迟**，等 ranked 人类对战真正有人用了再议。
- 协议和事件 schema 仍然为 realtime 预留位置：`clock.kind` 是枚举，`tick` 事件格式不变。到时候只需要新增时钟驱动，不需要再做破坏性变更。

**不在设计 17 范围内、但优先级更高的事项**：让环境可以在本地训练（游戏包能够 `pip install`，平台只负责评估、对战和回放）。远程训练每步一次往返，并且全平台共享 64 个并发环境，这是 P3 主旅程第一步的流失点。建议单独立项为设计 18。

## 1. 为什么推倒重来：现方案的根本问题

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| R1 | **时间模型不适合人类对局** | microrts `TIME_LIMIT=4000`（`packaged-games/microrts/env.py:40`），多数指令只持续 1 tick（`busy.remain=1`）；PvP 规则是双方都提交才推进；先提交的一方要靠 2s 轮询才能看到结果（`Pvp.jsx:40`） | 一局人类 PvP 理论上要 4000 次逐单位下令，加上每 tick 最多 2s 的轮询延迟，**根本打不完** |
| R2 | **计时存在但前端看不到** | `PVP_TIMEOUT=60s`，连续 5 次超时判负（`sessions.py:34`），只通过环境变量配置，API 不暴露 | 玩家会被一个看不见的规则判负；旧 spec 把这条写成了"不虚构计时" |
| R3 | **同一个概念在多处实现** | session 与 match 两个 id；会话回放与对局回放两种 schema；`opponent`、`controller`、`actions=null`、`kind=pve/pvp` 四路分叉；`/api/{game}/ai/action` 与 controller 两条 AI 路径；模型对战另开线程（`matches.py:334`） | 前端到处是分支，分享链接在对局结束时还会换 id |
| R4 | **推进依赖有人轮询** | 超时判定、tick 推进、落库都挂在 GET 上（`play_routes.py:132` 中的 `pvp_poll`、`_record_if_finished`） | 观战者在推动对局；没人轮询时对局永不结算，30 分钟后被 `cleanup` 静默删除，ELO 和对局记录都丢失 |
| R5 | **广播全量原始 state** | snake 的 state 自带 `seed`，食物位置由 `(seed, tick)` 决定；OpenEnv 对外开放 reset/step | 刷榜者可以离线预演出最优解；带隐藏信息的 UGC 游戏无法实现 |
| R6 | **回放靠客户端重算** | `replay.js` 每步一次 WS 往返，`moves ≥ 2000` 直接拒绝 | microrts 打满 4000 tick 的对局**无法回放**；回放还依赖旧版本游戏包一直可加载 |
| R7 | **前端按模式拆页面** | Play 663 行 + Pvp 1220 行 + Watch 241 行 + WatchReplay 327 行，各自实现轮询、合并、409 重同步 | 同一套状态逻辑写了 4 遍，旧 spec 的 12 种状态要在每个页面里各画一遍 |
| R8 | **鉴权不一致** | `/replay` 无鉴权；PvE 的 GET 不校验 owner；`session.side` 写死为 `"p0"` | 私有对局的动作序列可被读取；前端要靠手动覆盖 `side` 来规避 |

旧 spec 的隐含前提是"API 已经固定，舞台只负责映射"。但 R1、R2、R4、R6 都是 API 本身的缺陷，靠 UI 规则无法解决。

## 2. 第一性原理：舞台到底是什么

去掉具体页面，舞台只做三件事：

1. **展示一条权威帧时间线**：frame₀ → frame₁ → …，每一帧都是服务端算出的某个视角下的局面。
2. **如果我有座位，就为下一帧贡献输入**。
3. **展示时间**：下一帧什么时候产生，由谁决定。

于是：

| 旧模式 | 我有座位？ | 时间线状态 | 谁推进 |
|---|---|---|---|
| solo（PvE） | 有 | 增长中 | 我的输入（turn），或节拍（realtime） |
| duel（PvP） | 有 | 增长中 | 所有该出手的座位，或截止时间 |
| spectate | 无 | 增长中 | 同上 |
| replay | 无 | 已封存 | 本地播放头 |
| 模型对战 | 无 | 增长中或已封存 | 服务端座位，尽快推进 |

**四种模式其实是两个布尔值的组合**：`hasSeat` 和 `live`。UI 不需要 mode 这个属性，只需要从数据推导出能力位（§7.5）。

## 3. 领域模型

```
Match
├─ id: str                      创建即落库，贯穿 waiting → 回放的整个生命周期
├─ game, version                锁定版本（registry.resolve）
├─ mode: ranked | casual | practice     practice = 原 PvE，不计 ELO
├─ visibility: public | private | unlisted
├─ clock: {kind: turn|realtime, move_timeout_s?, tick_ms?, on_timeout, max_timeouts}
├─ seats: [Seat]
├─ status: waiting → active → finished | cancelled | aborted
├─ tick, frame (current authoritative state)
├─ log: [TickRecord]            每 tick 的输入（揭晓后）+ 引擎事件
└─ result: {winner: seat|null, cause, scores: {seat: n}}

Seat
├─ id: "p0" | "p1" | …          由游戏声明座位数（单人游戏只有 p0）
├─ occupant: {user_id, name} | null
├─ controller: human | ai{strategy} | model{model_id} | bot{url}
├─ presence: online | offline | server      由 SSE 连接推导
└─ timeouts: n
```

现有概念的归并：

- PvE 单机 = 1 个 human 座位。
- PvE 打 AI = p0 human + p1 ai。
- 模型代打 = p0 的 controller 为 model（occupant 仍是我）。对局中可以随时切换 controller，取代前端 `aiMode` 的 350ms 定时器。
- PvP = 两个 human 座位；房间就是有空座位的 waiting 对局；邀请码是 private 对局的入座凭证。
- 模型对战 = 两个 model 座位。不再需要单独的线程和 `model_vs_model` 分支。

**结果统一使用座位 id**：`winner: "p1"` 取代 `winner: 1`，前端不再需要拼 `"p" + winner`。

**生命周期**：

```
waiting ──座位坐满──▶ active ──引擎 done / 认输 / 超时判负──▶ finished
waiting ──房主取消 / 等待超时──▶ cancelled
waiting|active ──服务重启 / 沙箱熔断 / 空闲超时──▶ aborted（落库，带 cause）
```

所有终态都会落库。不再出现"会话消失，返回 404"的情况。

## 4. 后端设计

### 4.1 Match actor

每个非终态对局对应一个 asyncio 任务。这个任务持有对局的全部可变状态，并串行处理收件箱中的消息：

```
inbox:  Join | Submit(seat, tick, action) | Resign | Chat | SetController | RematchOffer | Timer
loop:
  cmd = await inbox.get(timeout = 下一个截止时间)
  apply(cmd) → 可能触发 resolve_tick()
  resolve_tick():
     服务端座位出招（ai / model / bot）
     frame' = await to_thread(adapter.step_state, frame, combined)
     append log; emit TickEvent; 重算 to_act / deadline
     done → 结算（ELO / XP / 榜单）→ 落库 → emit Finished → 封存帧
```

- **不再需要锁**：所有修改都在同一个任务内串行执行，取代现在散落各处的 `sess.lock` 和 `_STORE_LOCK`。
- **截止时间真正生效**：无论有没有人连着，超时都会触发。GET 回到纯读取。
- **结算只在一个地方发生**：取消 `_record_if_finished` 被 GET、actions、leave 三处调用的做法。
- **realtime 批量节拍**：同一个游戏的所有 realtime 对局对齐到同一个节拍，每个节拍调用一次 `step_batch`（适配器已经提供）。这一点很关键，因为每个游戏只有一个沙箱 worker，且由 `threading.Lock` 串行化（`ugc_runner.py:57`）；按对局逐个 step 会让吞吐随对局数线性下降。

### 4.2 时钟（游戏契约增量，见 §6）

| kind | 推进条件 | 输入语义 | 适用 |
|---|---|---|---|
| `turn` | `to_act` 中的座位全部提交，或到达 `deadline_at` | 每个 tick 一次，揭晓前可以修改 | 棋类、卡牌；snake/tetris 的"按键走一步"玩法 |
| `realtime` | 每 `tick_ms` 推进一次 | **意图**：座位最近一次提交的输入持续生效，直到被替换；游戏可声明 `intent: once`（只生效一 tick）或 `hold` | microrts 人类 PvP；真·实时贪吃蛇 |

- 超时策略由游戏在 game.yaml 中声明（`on_timeout: empty | forfeit`，`max_timeouts`），不再使用环境变量。
- realtime 模式下所有 controller 都是异步的意图提供者。外部 bot 迟到时沿用上一个意图，这样 2.5s 的 bot 超时不会卡住节拍。
- `tick_ms` 设平台下限（建议 100ms）。单个节拍超时就记延迟指标并跳过这一拍，不阻塞节拍。

### 4.3 视角

- 平台默认的视角函数：`view(state, seat) = 去掉所有 "_" 前缀键`。游戏包也可以提供 `view` 钩子做更细的裁剪（手牌、战争迷雾等）。
- 游戏作者把 RNG、seed 等不该下发的数据放到 `_` 前缀键下，平台不需要知道任何游戏名（满足 D26）。
- 对局 `finished` 之后，回放对所有有权查看的人下发完整 state（视角函数取 `None`），seed 随之公开，对局仍可复现。
- 可选：ranked 对局的观战流延迟 N tick 下发，防止有人给对局者实时报点。

### 4.4 持久化（D12 不变：进行中的状态在内存，记录落 SQLite）

- `matches` 表：创建时写入 id、game、version、mode、visibility、clock、status；结束时写入 result 和时间戳。
- `match_seats` 表：(match_id, seat, user_id, controller_json)，用于战绩、个人页和观战入口查询。
- 结束时封存帧：`data/replays/{id}.jsonl.gz`，每行一个 `{tick, frame, events, actions}`。按实测估算，microrts 初始 state 约 1.2KB，满局 4000 帧压缩后约 1MB 量级，这个规模存帧比服务端重算更简单。如果日后磁盘吃紧，再改成"动作日志 + 每 100 tick 一个关键帧"。
- 启动时把所有 `waiting/active` 的行标记为 `aborted(cause=server_restart)`。这比现在"重启后会话凭空消失"更诚实，也落实了 D12 的文案约束。

### 4.5 鉴权矩阵（一处定义，全部端点共用）

| 调用者 \ 对局 | public / 撮合 | unlisted | private |
|---|---|---|---|
| 座位占有者 | 读、写 | 读、写 | 读、写 |
| 已登录的其他人 | 读（观战视角） | 凭链接读 | 403 |
| 游客 | 读 | 凭链接读 | 403 |
| 结束后回放 | 同上 | 同上 | 仅座位占有者 |

practice 对局默认 `unlisted`，这样分享成绩时可以直接附上回放链接。

## 5. 协议（API v2）

### 5.1 命令（REST）

```
POST /api/v2/matches                          创建 {game, seats:[…], mode, visibility, settings}
POST /api/v2/matches/{id}/seats/{seat}/join   入座 {invite?}
POST /api/v2/matches/{id}/actions             {tick, action} → 202 {seq}
POST /api/v2/matches/{id}/controller          {seat, controller}   切换代打 / 托管
POST /api/v2/matches/{id}/resign
POST /api/v2/matches/{id}/rematch             第一次调用为发起，对方调用为接受；幂等
POST /api/v2/matches/{id}/chat                {text}
GET  /api/v2/matches/{id}                     快照（首屏、SDK、无流客户端）
GET  /api/v2/matches/{id}/frames?from&limit   历史帧（时间线、回放）；结束后可长期缓存
GET  /api/v2/matches?game&status=waiting&visibility=public    大厅，取代 /play/rooms
GET  /api/v2/me/matches?status=live           重连入口，取代 /play/active
POST/DELETE/GET /api/v2/{game}/matchmaking/*  语义不变，迁到 v2；matched 时返回 match_id
```

- `tick` 变为**必填**，它就是幂等键：同一个 (seat, tick) 重复提交，覆盖原提交而不是推进两次。旧的 `expected_tick` 可选语义随之取消。
- actions 只返回确认，**结果一律从流里到达**。客户端只需要维护一条状态更新路径。
- 错误码统一，并带机器可读的 `code` 字段：`409 stale_tick{current}`、`409 match_over`、`422 invalid_action{detail}`、`403 not_your_seat`、`403 not_to_act`、`429`。

### 5.2 事件流（SSE）

```
GET /api/v2/matches/{id}/stream        Last-Event-ID: <seq>
```

| type | 载荷 | 说明 |
|---|---|---|
| `snapshot` | 完整的 MatchView（§7.6）+ `server_time` | 每次连接的第一条；从某个 seq 续传时，如果缺口过大，也退化为 snapshot |
| `tick` | `tick, frame, events[], to_act[], deadline_at, actions?` | `actions` 在本 tick 揭晓后才下发 |
| `submitted` | `seat, tick` | 不带动作内容，防止对手偷看 |
| `timeout` | `seat, tick, count, max` | 用于"再超时 N 次判负"的警告 |
| `seat` | `seat, occupant, controller, presence` | 入座、离开、断线、代打切换 |
| `status` | `status, result?` | 包括 waiting→active、finished、aborted |
| `chat` | `id, from, text, at` | **聊天并入对局流**，取代 2s 聊天轮询 |
| `rematch` | `state: offered|accepted|expired, by, match_id?` | 对方会实时收到邀请 |
| `ping` | `server_time` | 每 15s 一次，防止 Cloudflare Tunnel 因空闲断开，同时用于校准时钟偏差 |

为什么选 SSE，而不是 WS 或轮询：

- **不用轮询**：R1 已经说明，轮询的延迟会叠加到每一个 tick 上。
- **不用 WS**：命令走 REST 可以复用现有的鉴权、限流、错误码和幂等机制。WS 需要自己实现请求和响应的对应关系（`openenv.js` 的注释已经点明它没有 response id）。SSE 天然的 `Last-Event-ID` 正好就是断线续传的语义。
- **鉴权**：用 `fetch` 读取流，可以携带 `Authorization` 头，不需要引入 cookie 或 ticket。
- **连接数**：单容器下每个连接只是一个 asyncio 队列，开销可以忽略。与 D12 一致。

## 6. 游戏包契约增量（game.yaml）

```yaml
seats: 2                       # 缺省 = pvp.enabled ? 2 : 1
clock:
  kind: realtime               # turn | realtime
  tick_ms: 250                 # realtime 必填，≥ 平台下限
  intent: hold                 # realtime：hold | once
  move_timeout_s: 30           # turn：单步时限；null = 不限（practice 默认）
  on_timeout: empty            # empty | forfeit
  max_timeouts: 5
# 可选的适配器钩子（不提供时平台给默认实现）：
#   to_act(state) -> [seat]    回合制游戏只让轮到的一方出手；默认 = 全部座位
#   view(state, seat|None)     默认 = 去掉 "_" 前缀键
```

- practice 和 ranked 可以使用不同的 clock（例如 snake 的 practice 用 turn 无时限，竞速榜用 realtime）。是否这样做属于产品决策，见 §10 Q2。
- D3 不受影响：clock 和 view 只存在于会话层，`step_state` 和训练面完全不动。

## 7. 前端设计

### 7.0 现状问题（证据：`docs/pm/qa/evidence/2026-10-23/stage-audit-before.png`）

| # | 问题 | 原因 |
|---|---|---|
| F1 | **棋盘只缩不放**：microrts 16×16 的棋盘在约 1300px 宽的深色井里只占约 200px，四周大片空黑 | `BoardFrame.jsx` 计算缩放时取 `Math.min(1, …)`，只缩不放；而且用的是 CSS transform，放大会发虚 |
| F2 | **四个页面四套布局**：试玩页侧栏是 CURRENT RUN / 排行榜 / 验证层，对战页是 MATCH INFO / 聊天，回放页的播放控件在右栏、离棋盘很远，观战页又是另一套 | 按模式拆页面（R7） |
| F3 | **输入和动作空间不匹配**：snake / microrts 单机给的是"动作（整数）"文本框；microrts 的指令构建器是一排指令按钮加 NESW，和棋盘上的单位脱节 | 控件没有按动作空间分型 |
| F4 | **状态靠说明文字传达**："双方都提交后回合推进""2s 轮询"写在控件下方；对手状态只是棋盘下方的一个小 chip | 协议里没有对应字段，只能用文案补 |

### 7.1 设计原则

1. **棋盘是主角**：棋盘占舞台主区域的大部分；深色井贴合棋盘，不留大块空黑。
2. **一个布局、五个槽位**，不按模式换页面。模式差异只体现为槽位的显隐和状态。
3. **状态出现在它所属的位置**：对手的状态在对手的座位卡上，时间在中央时钟上，结果在棋盘的覆盖层上。不靠说明文字。
4. **输入跟着动作空间走**，并尽量落在棋盘上，比如点单位下令。
5. **只显示协议给的字段**（保留旧 spec 的可追溯原则）。协议缺什么就补协议，不在 UI 里虚构。

### 7.3 槽位细节

**SeatCard（座位卡）**

| 状态 | 显示 | 数据来源 |
|---|---|---|
| 空座位 | 虚线卡 + "等待加入"；房主看到邀请码和复制链接，访客看到"入座"按钮 | `seats[].occupant == null` |
| 思考中 / 已提交 | 名字旁显示状态胶囊；已提交时显示 ✓ | `to_act`、`submitted` 事件 |
| 托管中 | controller 图标从人像变为芯片，并显示模型名 | `seat.controller` |
| 离线 | 在线点变灰，显示"离线 · 宽限 0:42" | `seat.presence` |
| 超时警告 | `超时 3/5`，转为 amber 色 | `timeout` 事件 |
| 胜 / 负 | 对局结束后显示 WIN / LOSS 胶囊 | `result.winner` |

HUD 中绑定了座位的项（如"金矿 P0"）放进对应的座位卡，需要在 HUD 声明里可选加一个 `seat: p0`。没有绑定座位的项（如分数、TICK）留在 HUD 条里。

**Clock（时钟）**

| 时钟 | 显示 |
|---|---|
| turn + 有时限 | 环形倒计时加秒数：剩 10s 转 amber，剩 5s 转 red；用 `deadline_at - (now + server_offset)` 计算 |
| turn 无时限 | 只显示 TICK |
| realtime | TICK + 每推进一帧闪一下的节拍点 + 速率（如"4 tick/s"） |
| 已结束 | 终局 TICK + 用时 |

**StageBoard（棋盘）**

- **放大算法**：`cell = floor(min(井宽 / W, 井高 / H))`，限制在 [12, 56] 之间，再把这个值作为 `cellSize` 交给 BoardCanvas 重新栅格化（它已经支持 DPR）。不再使用 CSS transform，所以放大后依然清晰。
- **井的尺寸**：井 = 棋盘尺寸 + 固定内边距，用棋盘自身的背景色。保留 Lab UI 的深色井规范，但不再出现大块空黑。
- **覆盖层**，按优先级只显示一个：
  1. 连接中断横幅（顶部细条，例如"正在重连 · 已缓存到 tick 412"）
  2. 回看横幅（例如"回看中 · tick 120 · 按 Esc 回到直播"）
  3. 等待卡（waiting 时显示在初始帧上，初始帧压暗）
  4. 结果卡（可以收起，露出终局棋盘）
- **交互图层**（只在复合动作游戏中出现）：选中框、目标格预览箭头、单位头顶的当前意图图标。

**ControlDock（出招控件）**：根据 meta 选择适配器

| 适配器 | 何时使用 | 交互 |
|---|---|---|
| KeyControls | 声明了 `controls.keys` | 显示键帽，按键即生效：turn 下直接提交，realtime 下设为意图；按下时键帽有反馈 |
| ChoiceControls | 声明了 `choices` 或带标签的 `actions` | 按钮组；turn PvP 中选中后可以修改，再提交 |
| DiscreteControls | `discrete(n)` 且没有标签 | n ≤ 12 时显示编号按钮；更大时用 stepper。**取消整数文本框** |
| CompositeBuilder | `composite per-unit` | 见下文 |

**CompositeBuilder（以 microrts 为例）**

1. 在棋盘上点己方单位即选中，Shift 加点可多选；空白处拖动可框选。
2. Dock 列出选中单位可用的指令，带快捷键：移动 M、采矿 H、返回 R、建造 B、生产 P、攻击 A、等待 W。
3. 方向可以点相邻格，也可以按方向键。棋盘上会预览目标箭头。
4. turn 模式下，指令进入"本 tick 待提交"列表，按 Enter 提交。
5. realtime 模式下，下令即更新意图，不需要提交按钮；单位头顶会显示当前意图图标，Dock 右侧显示"意图已同步 · tick 413"。

**提交状态**：turn 模式依次为 `编辑中 → 已提交（可修改，直到结算） → 已结算（棋盘闪一下）`；realtime 模式只显示"意图已同步"。收到 `409 stale_tick` 时，这次输入作废，并提示"已过期，请基于新局面操作"。

**Timeline（时间线）**

- **直播中**：显示一条细轨和"● LIVE"。拖动轨道就进入回看：棋盘显示历史帧，ControlDock 暂时禁用，并提示"回到直播再操作"。按 Esc 或点 LIVE 回到直播。
- **回放**：播放 / 暂停、单步、0.5–4x 倍速；键盘为空格、← →。
- **事件刻度**：轨道上标出死亡、攻击、超时、聊天等事件，点击即可跳转。
- **按需加载**：帧通过 `/frames` 分页加载，轨道上用浅色标出已缓冲的区间。

**SidePanel（侧栏）**

- **对局**：模式、可见性、版本、时钟规则、ELO 输赢预估、seed（结束后才显示）、分享链接。
- **聊天**：只有座位上的人能发言；观战者看不到聊天标签。
- **日志**：tick 推进、提交、超时、入座 / 离开等事件；回放时它就是动作流，点击可跳到对应帧。

**覆盖卡**

| 情况 | 内容 |
|---|---|
| waiting · 房主 | 邀请码（大号 mono 字）、复制链接、取消房间 |
| waiting · 访客 | 对局规则摘要 + "入座 p1" |
| finished | 胜 / 负 / 平、原因、ELO 变化；按钮依次为：再来一局、回看本局、分享、返回大厅 |
| rematch 邀请 | 结果卡上出现"maria 想再来一局 · 接受 / 忽略"，同时弹 toast |
| aborted | 中止原因（服务器重启 / 游戏熔断 / 空闲过久），给出返回入口 |
| 403 / 404 | 整个舞台显示空状态，说明原因 |

### 7.5 能力位（取代 mode 属性和 12 种手绘状态）

| 能力位 | 推导 |
|---|---|
| `canAct` | `you.seat && status==active && to_act.includes(you.seat) && controller(you.seat)==human && !reviewing` |
| `submittedThisTick` | 我的座位在当前 tick 的 `submitted` 为真（turn 模式下仍可修改） |
| `showClock` | `deadline_at != null`（turn）；realtime 显示节拍，不显示倒计时 |
| `showTimeline` | `!live`，或者用户主动打开（直播回看） |
| `showChat` | 有座位，且对局是多人对局 |
| `showRematch` | `status==finished && you.seat && 人类座位 ≥ 2` |
| `showShare` | `visibility != private` |
| `readOnlyReason` | 观战 / 已结束 / 未轮到我 / 托管中 / 回看中 / 已中止 |

旧 spec §5 的 12 种状态全部可以由这张表推导出来。Pen 稿只需要画**一个布局**，加上各槽位的状态变体。

### 7.6 代码结构

```
web/src/stage/
  matchStream.js     fetch 读 SSE：Authorization 头、Last-Event-ID 续传、退避重连、ping 看门狗
  reduceMatch.js     纯函数 reducer(events) → MatchView；可单测，回放和直播共用
  useMatch.js        hook：流 + reducer + 时钟偏差 + 命令（submit / resign / rematch / chat / setController）
  useFrames.js       帧缓冲 + 回看播放头 + /frames 分页
  capabilities.js    §7.5 的推导函数（纯函数，可单测）
  Stage.jsx          布局容器（variant: full | embedded）
  slots/             StageHeader, SeatCard, Clock, StageBoard, HudStrip, Timeline, SidePanel
  controls/          KeyControls, ChoiceControls, DiscreteControls, CompositeBuilder, pickControls.js
  overlays/          ConnectionBanner, ReviewBanner, WaitingCard, ResultCard, AbortedCard
```

- `variant="embedded"`：环境详情页的"试玩"标签、模型页的"挑战"直接嵌入 Stage。这时隐藏侧栏，Header 压成一行。
- BoardFrame 改为由 StageBoard 计算 `cellSize`，不再用 CSS 缩放。

`MatchView`（reducer 的输出，也是 GET 快照的形状）：

```
{ id, game, version, mode, visibility, clock, status, result,
  seats: [{seat, occupant, controller, presence, submitted, timeouts}],
  you: {seat | null},
  tick, frame, events, to_act, deadline_at,
  frames: RingBuffer | Lazy(frames API),
  chat: [...], rematch: {...} | null,
  server_offset_ms }
```

### 7.7 路由

- `/m/:id`：唯一的舞台路由。直播、观战、回放、分享都用它。
- `/games/:slug`：单机准备页，选择对手或代打模型 → `POST /matches` → 跳转到 `/m/:id`；也可以一键直接开局。
- `/games/:slug/pvp`：大厅（房间列表 / 快速匹配 / 邀请码）→ 跳转到 `/m/:id`。
- 旧路由 `/watch/*`、`/watch/match/*` 重定向到 `/m/:id`。

### 7.8 交互规则与无障碍

- 服务端权威，不做本地推演。提交后标记"已提交"，结果以 `tick` 事件为准。
- 只渲染游戏声明过的控件和 HUD（render v2 / D28 不变）。
- 页面隐藏时，流保持连接但暂停渲染；realtime 对局切到后台时，在座位上标记 presence=away。
- 用 `aria-live` 播报"轮到你""对手已提交""剩 10 秒""对局结束：你赢了"；倒计时同时提供文字，不只靠颜色。
- 全键盘可操作：Tab 在槽位之间切换，Enter 提交，Esc 回到直播或取消选择；`prefers-reduced-motion` 时关闭棋盘动效和节拍闪烁。

| M4 SDK 与数据 | SDK 改用 v2 并发布大版本；运行一次性离线迁移脚本（见下） | 仓库中 grep 不到 `play/sessions`、`expected_tick`、`rebuildReplay` |

**数据迁移**（这是数据迁移，不是 API 兼容）：

- 旧 `matches` 表中的已结束对局：脚本用对应版本的适配器在服务端重算一遍，生成封存帧并写入新表。重算失败的对局标记为 `replay: unavailable`，只保留结果。
- 旧 `scores` 榜单：原样保留（Q1 已关闭，snake / tetris 的玩法不变）。
- ELO、XP、好友、聊天历史等不受影响。
- 上线时，内存里正在进行的会话本来就会因重启丢失（D12），不需要额外处理。

**对外影响**：旧版 SDK 和第三方 bot 调用 `/api/v1/*/play/*` 会直接收到 404。发布说明里必须写明 SDK 的最低版本，以及 v1 到 v2 的字段映射。

## 11. 不做 / 风险

- **不做**：多副本或 Redis（D12 演进项）；WebRTC；客户端预测或回滚（服务端权威 + 100ms 以上的节拍不需要）。
- **风险：沙箱吞吐**。每个游戏只有一个 worker，且串行执行。realtime 对局数 × 节拍频率受它限制，需要用 `step_batch` 合批，并在 M3 加上每个节拍的耗时指标；必要时为每个游戏开多个 worker。
- **风险：SSE 经过 Cloudflare Tunnel**。需要关闭响应缓冲（`X-Accel-Buffering: no`，且不能套 GZip 中间件），并保持 15s ping。M1 需要在线上环境实测一次。
- **风险：一刀切换没有回退余地**。上线前在预发环境完整跑一遍 06 用例矩阵和 browser_acceptance；保留上一个版本的镜像，以及迁移前的数据库备份（`deploy/backup.sh`），出问题时整体回滚，而不是新旧混跑。
- **风险：封存帧的磁盘占用**。按每局约 1MB 估算，每 1 万局约 10GB。需要加入备份脚本（D15），并设定保留策略，例如 casual 对局 90 天后降级为只存动作日志。
