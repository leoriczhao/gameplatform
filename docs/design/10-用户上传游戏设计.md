# 10 · 用户上传游戏（UGC 游戏库）设计

> **历史设计，不作为当前环境 API 手册。** 本文保留当时的决策、接口示例与验收记录；
> 环境交互相关内容已被 [OpenEnv 契约](../api/openenv.md) 取代。旧环境 API 已删除，
> 不保留兼容；当前架构见 [架构总览](../architecture.html)，平台业务与回放见
> [运行时契约](../api/runtime-contracts.md)。下文不代表本次切换已部署或通过测试。

> 状态：已交付（历史设计，2026-08）· 对应实现：[11-用户上传游戏实施计划](./11-用户上传游戏实施计划.md)
> 动机：用户希望「用户可以自己上传游戏 + 各种 API」，并明确权限与安全是核心关切。

## 1. 目标与范围

让**注册用户**自助上传自己实现的游戏（Python 包 + 元数据），经**管理员审核**后进入公共游戏库，
与内置游戏一样获得平台能力：网页可玩（PvE + **PvP 房间/快速匹配/ELO**）、榜单、内置 AI、观战/回放、ONNX 模型托管。

**已确认的决策**（用户拍板，2026-08）：

| # | 决策点 | 选择 |
|---|---|---|
| D17 | 上传形态 | Python 包（zip：EnvAdapter 实现 + `game.yaml` 元数据），官方 GDK 模板 + 本地测试器 |
| D18 | 运行隔离 | **受限子进程沙箱**：每游戏一个受限 Python 进程，纯函数 JSON 协议，禁网络/文件写，CPU/内存/超时限制，超限熔断 |
| D19 | 发布流程 | 双轨：注册用户上传「草稿」（仅自己可见可测）→ 管理员审核 → 公开发布；随时可下架 |
| D20 | 作者门槛 | 所有注册用户即可上传草稿 |
| D21 | 功能范围 | v1：PvE 游玩 + 榜单、内置 AI（opponent_action）、ONNX 契约、观战/回放、**PvP 房间 + 快速匹配 + ELO**（能力声明制，见 §7）；不含自定义图片/音效资源 |
| D22 | 渲染 | 通用 JSON 棋盘渲染器（`game.yaml` 声明 grid/cells/units + 纯文本/emoji 元素） |
| D23 | 配额与熔断 | 草稿 ≤5 个/人、公开 ≤3 个/人；包 ≤20MB；step 超时 200ms、内存 512MB、无网络；连续超限自动熔断暂停 |
| D24 | 版本管理 | 版本号 + 变更日志；每次更新重新走审核；审核期间旧版本继续服务 |

## 2. 对标依据（权威平台用户用例）

- **Board Game Arena（最贴近）**：开发者计划 → pre-alpha 自研 → **alpha 官方评审 + 测试者批准** →
  **beta 需 10+ 批准且评分 ≥4.5（管理员可酌情）** → gold 正式发布；发布后可修 bug。
  我们简化生命周期为 草稿→审核→公开（规模小，不做评分门槛，管理员终审）。
  来源：https://en.doc.boardgamearena.com/Steps_to_create_a_BGA_game
- **Roblox/Luau**：平台内嵌沙箱 VM——不可信代码不能访问系统；移除 io/package/os.execute、
  禁字节码、**中断机制限 CPU**、特权隔离。我们的「受限 Python 子进程」是对应的进程级方案。
  来源：https://luau.org/sandbox/
- **Steam Workshop / itch.io**：创作者自助上传 + 平台内容审核 + 拥有者全生命周期（更新/下架）+ 举报移除。
  来源：https://partner.steamgames.com/doc/sdk/uploading 、https://itch.io/docs/creators/quality-guidelines
- **沙箱技术光谱**：V8 isolate（Cloudflare Workers）< gVisor/nsjail < Firecracker 微 VM（Fly.io/AWS Lambda）。
  我们取「进程 + rlimit + 白名单 runtime」这一档：实现成本可控、隔离强度满足审核制场景。
  来源：https://stealthcloud.ai/glossary/v8-isolate/

## 3. 架构总览

```
作者 ──上传 zip──▶ ugc.py（校验/静态扫描/版本表）
                        │ 草稿（仅作者可见，可在沙箱内自测）
                        ▼
管理员 ──审核──▶ status: pending → published（公开）
                        │
运行时：FastAPI ──▶ registry（内置 adapter + UGC 代理 adapter）
                        │
        ┌───────────────┴─────────────────────────┐
        │  UGC Worker 池（每游戏一个受限子进程）      │
        │  newline-JSON over stdio，rlimit 限制       │
        │  new_state/step_state/ai_action 纯函数调用  │
        └───────────────┬─────────────────────────┘
平台能力：/api/{slug}/env/* · /play · /scores · /ai · 观战回放 · ONNX 契约
前端：大厅目录 + 通用 JSON 棋盘渲染器（UgBoard/UgPlay 页面）
```

**关键设计**：UGC 游戏在 `registry` 中注册的是 **ProxyAdapter**（实现 EnvAdapter 接口，
内部通过 IPC 调用沙箱 worker），因此 env API、play 会话、榜单、观战回放等全部既有路由
**零改动自动生效**——这正是「一个引擎原则（D3）」在 UGC 上的延续。

## 4. 包规范（GDK-UG）

zip 内结构（≤20MB，文件 ≤200 个）：

```
mygame.zip
├── game.yaml          # 元数据 + 渲染声明 + 契约声明（见下）
├── __init__.py        # 暴露 get_adapter() -> EnvAdapter 实例
├── ...你的代码.py      # 仅允许 .py/.json/.yaml/.txt 文本文件
└── README.md          # 玩法说明（可选，展示在游戏详情）
```

`game.yaml` 必填项（**slug 创建后不可修改**；改名 = 新游戏）：

```yaml
slug: my-game            # 全局唯一，字母数字连字符；不与内置 snake/tetris/microrts 冲突
title: 我的游戏
description: 一句话介绍
version: 1.0.0
# 渲染声明（通用 JSON 棋盘渲染器，D22）：
board:
  width: 10
  height: 10
  palette:               # cell 类型 → 显示（emoji 或字符 + 颜色）
    empty: { glyph: "·", color: "#e4e4e7" }
    wall:  { glyph: "🧱" }
    apple: { glyph: "🍎" }
  units:                 # 可选：state.units 的元素类型 → 显示与朝向
    snake: { glyph: "🟢" }
# ONNX 托管契约（D21，可选；声明后玩家模型可上传打这个游戏）：
contract:
  in_shape: [1, 64]
  out_shape: [1, 4]
# 内置 AI（D21，可选）：声明策略名列表，get_adapter() 实现 opponent_action
ai_strategies: ["greedy"]
# PvP（D21，可选）：声明后该游戏开放房间/快速匹配/ELO 榜
pvp:
  enabled: true
  action: unit            # v1 两种形态二选一：
                          #   unit   = 棋盘复合指令 [unit_id, cmd, dir?, type?]（state 含 units）
                          #   choice = 每回合双方各选一个动作（choices 按钮组）
  # action: choice
  # choices: ["石头", "剪刀", "布"]
```

**PvP 契约要求**（声明 `pvp.enabled` 的作者必须满足）：`step_state` 与 `validate_action`
必须接受**复合动作** `{"p0": …, "p1": …}`（unit 型两侧各为指令列表；choice 型各为单个
动作索引）；双方都提交后平台按现有 PvP 协议推进一 tick——与内置 microrts 完全同构。

**state 输出约定**（通用渲染器依赖）：state 顶层必须含
`board: [[cell_id, …]×h]`（cell_id 与 palette 对应）；可选 `units: [{id,x,y,type,…}]`。
其余字段（bank/damage/tick…）自由。此约定不影响训练面；上传校验器与沙箱内
`validate_state` 都会校验 board 形状与 palette 一致（防渲染崩溃）。

`ai_strategies` 声明后，平台自动挂载 `/api/{slug}/ai/action`（ProxyAdapter 提供通用
pydantic 请求模型，转发给沙箱内的 `opponent_action`/`ai_action` 实现）。

## 5. 安全模型（核心章节）

**五层防线，纵深防御**：

1. **包静态校验**：白名单扩展名（仅文本类，**禁 .so/.pyd/.dll 等二进制扩展**）；
   zip 内路径穿越检测；大小/文件数限制。
2. **AST 静态扫描**（上传时）：解析全部 .py，白名单 import——**Python 标准库白名单子集 + numpy**
   （运行环境固定为平台 venv，作者**不可自带第三方依赖**、不可带二进制扩展）；
   拒绝 `socket/subprocess/os.system/os.spawn/shutil.rmtree/ctypes/open(写模式)/eval/exec/compile/__import__` 等；
   拒绝对包外路径的读。**作者必须在受限 API 面内实现纯函数**。
3. **受限子进程**：worker 以独立进程运行；`resource.setrlimit`（RLIMIT_AS=768MB、RLIMIT_CPU、RLIMIT_FSIZE、RLIMIT_NPROC=128）；
   沙箱内强制 `OPENBLAS_NUM_THREADS=1`（2026-08 G2 实测校准：numpy 2.x import 需 ≥768MB 虚拟地址空间，
   OpenBLAS 默认 16 线程会撞 NPROC 限制导致 import 级联失败；单线程 BLAS 也更利于确定性）；
   启动前 `setsid`；无网络依赖的 runtime（runners 注入：socket 等模块被替换为抛错桩）；工作目录只读。
4. **纯函数协议 + 超时**：每次 IPC 调用（new_state/step_state/ai_action）都是 `请求JSON行 → 响应JSON行`，
   默认 **200ms 超时**，超时/崩溃即 kill 并熔断计数；输入输出严格 schema 校验。
5. **审核 + 举报 + 熔断**：公开发布必须过管理员审核（人肉终审代码与内容）；复用现有举报系统；
   连续超限自动 `paused` 并通知作者与管理员；封禁作者 = 其游戏全部下架。

**诚实声明残留风险**：进程级 rlimit 沙箱**不是**微 VM 级隔离——理论上存在
rlimit 绕过、CPU 侧信道、Python 解释器 0day 等逃逸面。缓解 = 上述 1/2/5 层 + 禁止二进制扩展 +
审核制（恶意作者很难过审，过审后作恶会被熔断/下架/封号）。若未来创作者规模扩大，
可平滑升级为 Firecracker/gVisor（协议不变，只换 runner 底层，见 11 的演进路径）。

## 6. 数据模型（沿用 `_db()` 模式）

```sql
CREATE TABLE IF NOT EXISTS ugc_games (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  owner_id INTEGER NOT NULL,
  slug TEXT NOT NULL UNIQUE,
  title TEXT NOT NULL,
  description TEXT,
  status TEXT NOT NULL DEFAULT 'draft', -- draft|pending|published|banned|paused
  pause_reason TEXT,
  created_at REAL NOT NULL, updated_at REAL NOT NULL);

CREATE TABLE IF NOT EXISTS ugc_versions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  game_id INTEGER NOT NULL,
  version TEXT NOT NULL,
  changelog TEXT,
  package_path TEXT NOT NULL,   -- 解包目录（MODELS_DIR 同卷）
  meta TEXT NOT NULL,           -- game.yaml 解析结果 + 包 sha256 + 扫描报告
  status TEXT NOT NULL DEFAULT 'draft', -- draft|pending|active|superseded|rejected
  review_note TEXT,
  reviewer_id INTEGER,
  created_at REAL NOT NULL);
```

配额口径（D23）：**按游戏数计**——作者名下 `draft/pending/published` 状态的游戏总数 ≤5，
其中 `published` ≤3；版本数不计入配额。

## 7. API 设计（v1）

**作者面（登录用户）**：
```
POST   /api/v1/ugc/games            multipart 上传 zip → 校验+扫描+沙箱 smoke（new_state+10 step）→ 草稿
GET    /api/v1/ugc/games            我的游戏（含状态/版本）
POST   /api/v1/ugc/games/{id}/versions   上传新版本（版本号递增，重新走审核）
POST   /api/v1/ugc/games/{id}/submit     草稿 → pending（提交审核）
DELETE /api/v1/ugc/games/{id}            删除草稿（已公开的不可直接删，需下架申请）
POST   /api/v1/ugc/games/{id}/test       在沙箱内跑自定义测试脚本（可选）
```

**公开面**：`GET /api/v1/ugc/games?status=published`（目录，含 title/author/描述）；
大厅 `GET /api/games` 合并 published UGC 条目（带 author 与 ugc 标记）。

**管理员面（/api/v1/admin/ugc/*，role=admin）**：
```
GET    ...?status=pending         审核队列
POST   /{id}/approve              审核通过 → 版本 status=active、游戏 published
POST   /{id}/reject               驳回（必填 review_note）→ 退回 draft
POST   /{id}/ban / /unban         下架/恢复（ban 后对玩家 404、作者可申诉）
POST   /{id}/pause / /resume      熔断暂停/恢复（超限自动 pause）
POST   /{id}/rollback             回滚到指定历史版本（version_id）→ 该版本重新 active
POST   /{id}/retest               审核前在沙箱重跑 smoke（附报告）
```

作者对已公开游戏：可 `POST /api/v1/ugc/games/{id}/unpublish` **自行下架**（立即对玩家隐藏，
回到 draft，保留版本可再次提交审核；admin 也会收到一条通知留痕）。
物理删除仅限 draft 状态（`DELETE`，D23 配额随删释放）。

**游玩面**：与内置游戏完全同构——`/api/{slug}/env/*`、`/api/v1/{slug}/play/sessions`（游客可玩，
与内置一致）、`/api/{slug}/scores`（PvE 分数榜）、
`/api/{slug}/ai/action`（声明了 `ai_strategies` 即自动挂载）。

**PvP（D21 修订：v1 即支持）**：声明 `pvp.enabled` 的 UGC 游戏自动开放
`/api/v1/{slug}/play/rooms`、`/api/v1/{slug}/matchmaking/queue` 与 `/api/v1/{slug}/ratings` ELO 榜，
ranked/casual、断线重连、再来一局、观战回放全部复用既有实现。
**现有 `sessions.create_pvp_session` 与 `matchmaking.join_queue` 里硬编码的 microrts 白名单
改为能力声明检查**（`adapter.pvp_enabled`：内置 microrts=true，snake/tetris=false，UGC 读 meta）。
这是本修订对既有代码的唯一侵入点，已计入 11 的 P4。

**观战与回放**：观战走既有 `/watch/{slug}/{sessionId}`（PvE 会话凭 session id 可围观，与内置一致）。
回放需要**新增 PvE 对局落库**——现有 `matches` 只落 PvP（`record_pvp_finish`），
v1 必须补 `record_pve_finish`（kind=pve，存 seed+moves+result，公开只读回放端点放行 pve），
否则 UGC 的「观战+回放」承诺无法兑现。此为本设计与现网代码核对的**关键缺口**，已计入 11 的 P4。
**保留策略：全部保留，不设上限**（当前对局规模下 matches 增长可控）。

**模型面**：`/api/v1/models` 上传时若 game 为 UGC，契约从该游戏 `meta.contract` 读取并校验。

## 8. 生命周期与状态机

```
上传 ─▶ draft（仅作者可见，可测/可删/可更版）
          │ submit
          ▼
       pending（管理员审核队列；期间旧 active 版本继续服务）
        ╱          ╲
   approve        reject（review_note 退回 draft）
        ╲          ╱
         ▼
      published（进大厅/目录，可玩/上榜/PvP/观战/回放/模型）
        │         │
   unpublish    ban      （unpublish=作者自行下架→draft；ban=管理员下架，作者可申诉）
     (→draft)   (下架)   
        │
     ┌──┴────────────┐
   pause            新版本（旧 active → superseded 保留可回滚）
   (熔断：连续超时/超内存；admin 可恢复)
```

封禁作者（现有 admin 用户封禁扩展）：其全部 UGC 游戏自动下架（worker 停止，包文件保留备查）。

**通知链路**：审核通过 / 驳回（含 review_note）/ 下架 / 熔断 / 作者下架申请，全部走既有
notifications 发站内通知给作者（admin 操作留 reviewer_id 审计）。

## 9. 前端

- **通用渲染器** `components/UgBoard.jsx` + `web/src/render/`：读 `game.yaml` 声明渲染 state；
  渲染 v2（2026-09，设计 16）升级为 Canvas 主渲染 + DOM 回退，支持精灵/矢量/朝向/归属色/血条/
  图层/动效/HUD 与可选沙箱渲染器。
- **PvP 交互组件** `pages/UgPvp.jsx`：unit 型复用现有 PvP 页的「选单位→方向/指令→提交」交互，
  渲染与指令集由 game.yaml 数据驱动；choice 型渲染按钮组（每回合选一个提交）。
  双方提交→推进 tick、超时判负、认输、再来一局、房间聊天等全部复用既有 PvP 页面逻辑。
- **页面** `pages/UgPlay.jsx`：上传的游戏统一入口（/games/ugc/{slug}）——人工打 PvE + 内置 AI 演示 +
  提交分数；`pages/UgUpload.jsx`：作者工作台（上传/版本/提交审核/测试日志）。
- **大厅**：UGC 游戏卡片与内置游戏混排，带「作者」标签；详情页展示 README/版本/变更日志；
  新发布游戏进入「新上线」分组（按发布时间排序，置顶轮播后续再议）。
- **游客**：公开 UGC 游戏与内置一致，游客可直接玩 PvE（上传/管理需登录）。
- **管理后台**：新增「UGC 审核」tab（审核队列/通过/驳回/下架/熔断恢复）。

## 10. 管理员审核清单（approve 前逐项核对）

- [ ] 静态扫描报告无高危项（§5 第 1/2 层）
- [ ] 沙箱 smoke 通过（new_state + ≥10 step，200ms/512MB 内；admin 可 `retest` 重跑）
- [ ] `game.yaml` 完整：slug 不与内置/既有游戏冲突、渲染声明可解析、README 齐全
- [ ] 实际试玩：PvE 一局可完赛、分数可上榜、AI（如声明）动作合法
- [ ] 内容合规：无违规内容/外链诱导/侵权素材（参照平台公告与举报规则）
- [ ] 有 ONNX 契约声明时：契约 shape 与 obs/动作空间一致（示例模型能加载）
- [ ] 声明 `pvp.enabled` 时：双账号走一遍 房间创建/加入→推进 tick→结算（ranked ELO、casual 不计分）
